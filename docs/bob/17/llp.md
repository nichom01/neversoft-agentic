# Low-level plan: #17 open telemetry

## Overview
The approved high-level plan scopes this to `tools/warehouse-server` (Fastify 5 + `node:sqlite`, ESM, run through `tsx`). The server is built in [`app.ts`](../../../tools/warehouse-server/src/app.ts) (`buildApp`) and started in [`index.ts`](../../../tools/warehouse-server/src/index.ts). Today `package.json` has `dev: tsx watch src/index.ts` and `start: tsx src/index.ts`, and there is no signal handling and no README in the server folder.

Design:
1. A new pure-ish module `src/telemetry.ts` holds config resolution, SDK creation, start and shutdown. It imports only OpenTelemetry packages. It never imports `fastify` or `node:http`, so tests and `index.ts` can import it safely.
2. A new side-effect module `src/instrument.ts` is preloaded with `--import` in `dev` and `start`. It calls `initTelemetry()` before `index.ts` loads Fastify or `node:http` (AC-9). When no collector endpoint is configured it does nothing and imports no SDK code paths that open sockets (AC-1).
3. Telemetry is enabled only when an OTLP endpoint env var is set. Exporters are chosen by the SDK from standard `OTEL_*` variables (`OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_TRACES_SAMPLER`, `OTEL_SERVICE_NAME`). The repo code only validates the endpoint and sets a default `service.name` (AC-5, AC-6).
4. Instrumentations are `@opentelemetry/instrumentation-http` (server span, status, HTTP server metrics) and `@fastify/otel` created with `registerOnInitialization: true` (route names). That mode hooks Fastify's `fastify.initialization` diagnostics channel, so it needs no change to `buildApp` and also works for `app.inject` in tests, provided `initTelemetry` runs before `buildApp`.
5. `index.ts` registers `SIGINT` and `SIGTERM` handlers that close the app, then call `shutdownTelemetry()` with a bounded timeout (AC-8).
6. `app.ts` stays unchanged unless the 4xx check in the tests fails (see the contingent entry below).

Exact package versions are not fixed in this plan. The implementer must run `npm install` for the latest stable releases, confirm that `@opentelemetry/*` experimental (`0.x`) and stable (`2.x`/`1.x`) lines are mutually compatible, and run `npm audit`. The lock file pins them (AC-13). No tool in this planning stage can query the registry, so version numbers are deliberately not stated.

### tools/warehouse-server/src/telemetry.ts (create)
- Holds all telemetry logic. Module-level `let sdk: NodeSDK | undefined` so the preload and `index.ts` share one instance (both resolve to the same URL, so they share one module instance).
- `resolveTelemetryConfig(env)`:
  - Disabled (`{ enabled: false }`) when `OTEL_SDK_DISABLED` is `"true"` (case-insensitive) or none of `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` is set to a non-empty value.
  - For each endpoint that is set, parse with `new URL`. Accept it only if the protocol is `https:`, or the protocol is `http:` and the hostname is one of `localhost`, `127.0.0.1`, `[::1]`. An unparsable or non-local `http:` endpoint returns `{ enabled: false, reason }`. The reason names the variable and the rule only. It never includes the URL, userinfo or any header value (AC-5, AC-6).
  - Otherwise `{ enabled: true, serviceName: env.OTEL_SERVICE_NAME || "warehouse-server" }`.
  - Fail closed: an invalid config leaves telemetry off and the server running. It does not throw.
- `initTelemetry(env = process.env, overrides?: TelemetryOverrides): TelemetryHandle | undefined`:
  - Call `resolveTelemetryConfig`. If disabled with a `reason`, emit one `console.warn("telemetry disabled: <reason>")`. If disabled without a reason, return `undefined` silently (AC-1).
  - If already started, return the existing handle (idempotent).
  - Build `new NodeSDK({ serviceName, instrumentations: [new HttpInstrumentation({...}), new FastifyOtelInstrumentation({ registerOnInitialization: true })], ...overrides })`.
  - `HttpInstrumentation` options: do not set `requestHook`, `headersToSpanAttributes` or any option that adds headers or bodies. Default semantic-convention attributes only (AC-10). Add `ignoreIncomingRequestHook` only if static-asset requests turn out to be noisy; do not add it speculatively.
  - Exporters come from the SDK's env-driven selection: no explicit exporter is constructed unless `overrides` supplies one. This keeps endpoint, protocol, headers and sampler entirely in `OTEL_*` variables (AC-5).
  - Exporter timeout: if neither `OTEL_EXPORTER_OTLP_TIMEOUT` nor the signal-specific timeout vars are set, the SDK default (10 s) already bounds exports. Do not raise it. Do not mutate `process.env`.
  - Call `sdk.start()` inside a `try/catch`. On failure, `console.warn("telemetry disabled: SDK failed to start")` (no error details that might carry endpoint data), set `sdk = undefined`, and return `undefined`. The server must still start (AC-7).
  - Return `{ shutdown }`.
- `shutdownTelemetry(timeoutMs = 5000): Promise<void>`:
  - No-op when not started.
  - `Promise.race([sdk.shutdown(), timeout])`, swallow rejection (log nothing sensitive), clear `sdk`. The timer must be `unref`'d or cleared so it cannot keep the process alive (AC-6, AC-8).
- Exports: `resolveTelemetryConfig`, `initTelemetry`, `shutdownTelemetry`, types `TelemetryConfig`, `TelemetryOverrides`, `TelemetryHandle`.
- `TelemetryOverrides` is `Partial<Pick<NodeSDKConfiguration, "spanProcessors" | "traceExporter" | "metricReader">>`. Use the property names of the installed `@opentelemetry/sdk-node` version (some versions use `metricReader`, newer ones `metricReaders`). It exists only so tests can inject in-memory exporters with no network.
- Symbols: `resolveTelemetryConfig`, `initTelemetry`, `shutdownTelemetry`, `TelemetryConfig`, `TelemetryOverrides`, `TelemetryHandle`
- Covers: AC-1, AC-2, AC-3, AC-4, AC-5, AC-6, AC-7, AC-8, AC-10, AC-13

  ```ts
  let shuttingDown = false;
  for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.on(signal, async () => {
      if (shuttingDown) return;
      shuttingDown = true;
      await app.close();
      await shutdownTelemetry();
      process.exit(0);
    });
  }
  ```

  - `OTEL_SDK_DISABLED=true` with an endpoint gives disabled

- Component, in-process spans with an in-memory exporter and no network: call `initTelemetry({ OTEL_EXPORTER_OTLP_ENDPOINT: "http://127.0.0.1:1" }, { spanProcessors: [new SimpleSpanProcessor(memoryExporter)], metricReader: <PeriodicExportingMetricReader over InMemoryMetricExporter, short interval> })` before calling `buildApp(new WarehouseDb(":memory:"))`.   - `POST /api/vehicles` with a body containing a VIN and `GET /api/vehicles?make=Ford`: assert that no span attribute key or value contains the VIN or the request body, and that no attribute holds a `url.query` or `http.url` containing the query string. This assertion is limited to what is observable with `inject`, and the child-process test repeats it over real HTTP (AC-10)
  - `shutdownTelemetry()` flushes, and the metric exporter has received at least one data point with a request count or duration metric after `forceFlush`/shutdown (AC-3, AC-8). If `inject` does not drive the HTTP-server metrics because they come from `instrumentation-http`, move this assertion to the child-process test.
- Because the SDK registers global providers, tests in this file must run sequentially and end with `shutdownTelemetry()` plus `trace.disable()`/`metrics.disable()` from `@opentelemetry/api` so that other suites in the same `tsx --test` run are unaffected. `tsx --test` runs each file in its own process, so isolation across files is already given.

### tools/warehouse-server/src/telemetry.e2e.test.ts (create)
- Spawns real server processes with `node:child_process` `spawn`, so it exercises the real preload path (`tsx --import ./src/instrument.ts src/index.ts`, the same command as `npm run start`) and real `node:http` (AC-9).   6. Non-local plain-HTTP endpoint (`http://collector.example.com`): server starts, serves a request, prints one `telemetry disabled` warning without the URL, and makes no attempt to connect (AC-6).
  7. 5xx: needs a way to force a 500 through the real stack, which `index.ts` does not offer. ## Interfaces
```ts
// tools/warehouse-server/src/telemetry.ts
export type TelemetryConfig =
  | { enabled: true; serviceName: string }
  | { enabled: false; reason?: string };

export interface TelemetryOverrides {
  spanProcessors?: SpanProcessor[];
  traceExporter?: SpanExporter;
  metricReader?: MetricReader; // property name follows the installed sdk-node version
}

export interface TelemetryHandle {
  shutdown(): Promise<void>;
}

export function resolveTelemetryConfig(env: NodeJS.ProcessEnv): TelemetryConfig;
export function initTelemetry(
  env?: NodeJS.ProcessEnv,
  overrides?: TelemetryOverrides,
): TelemetryHandle | undefined;
export function shutdownTelemetry(timeoutMs?: number): Promise<void>;
```
No HTTP routes, events or response shapes change. No new listening ports.

None has a committed default value, except `service.name`, which defaults to `warehouse-server`.
- No feature flag beyond the endpoint variable. Telemetry is off when it is unset.
- `package.json` scripts `dev` and `start` change; `package-lock.json` changes.

## Rollout
1. Install dependencies in the workspace (`npm install -w @warehouse/server ...`), regenerate the root `package-lock.json`, run `npm audit`.
2. Add `telemetry.ts`, `instrument.ts` and the `telemetry.test.ts` unit tests. Confirm the config logic passes before touching start scripts.
3. Wire `package.json` scripts and `index.ts` shutdown. Verify preload ordering with the e2e test. Resolve the two known uncertainties at this step: whether `tsx --import` preload works as written, and whether ESM loader hooks are needed for `node:http`.
4. Add the in-process span tests and the fixture. If a 4xx span is marked `ERROR`, apply the contingent `app.ts` change.
5. Write the README.
6. Run `npm run typecheck`, `npm run test:warehouse`, and `npm test -w @warehouse/server`.
- Backwards compatibility: with no `OTEL_*` variables, behaviour, ports, and responses are identical. The only visible difference is the `SIGINT`/`SIGTERM` handler, which now closes the app before exit. Existing tests build the app through `buildApp` and never import `instrument.ts`, so they need no collector. There is no flag to remove, and reverting is a matter of removing the preload from the two scripts.

## Open questions
- The high-level open questions remain unresolved and this plan keeps the stated assumptions: server only, OTLP over HTTP (JSON or protobuf chosen by `OTEL_EXPORTER_OTLP_PROTOCOL`, gRPC not documented as supported), traces and metrics both included, and no `WarehouseDb` spans.
- Does `@fastify/otel` with `registerOnInitialization: true` mark handled 4xx errors as `ERROR`? The component test decides this, and the contingent `app.ts` change is the fallback.
- Does the installed `@opentelemetry/sdk-node` start a metric reader automatically from env? If not, add an explicit `PeriodicExportingMetricReader` with an OTLP metric exporter inside `initTelemetry` only, keeping endpoint and headers env-driven.
